# ReMap game scripts

ReMap maintains one source file per Squirrel module and builds two isolated distributions:

- `scripts/vscripts/remap_r5r/` for R5Reloaded;
- `scripts/vscripts/remap_r5f/` for R5Flowstate.

Copy the contents of the selected distribution to `platform/scripts/vscripts/remap/` in the target game. The distribution folder name is not part of the installed script path.

| Module | Scope | Purpose |
| --- | --- | --- |
| `sh_remap` | Server + client | Initialization, map precache and context-aware cleanup |
| `sv_remap_objects` | Server | Prop creation and prop ownership |
| `sv_remap_ziplines` | Server | Zipline creation and zipline ownership |
| `cl_remap_objects` | Client | Client-side prop creation and ownership |
| `sv_remap_map` | Server | Server-side map objects generated by the Unity app |
| `cl_remap_map` | Client | Client-side map objects generated by the Unity app |

Public helpers use `ReMap_`; context entry points use `Sh_ReMap_`, `Sv_ReMap_`, and `Cl_ReMap_`. R5Reloaded calls `Sh_ReMap_Init()` from `sh_init.gnut`; R5Flowstate calls it from `_sh_init.gnut`. The app writes precaches inside `Sh_ReMap_PrecacheMap()`, server entities inside `Sv_ReMap_LoadMap()`, and client entities inside `Cl_ReMap_LoadMap()`.

## One module per source, two safe variants

Each generated file has its own matching source under `scripts/vscripts/source/`:

- `sh_remap.source.nut`;
- `cl_remap_objects.source.nut`;
- `sv_remap_objects.source.nut`;
- `sv_remap_ziplines.source.nut`.

The editable reset templates `sv_remap_map.nut` and `cl_remap_map.nut` are copied to both distributions as well.

Use `#if R5R` or `#if R5F` inside any source when only one game supports a section. `#else` and nested guards are supported. Guards are removed from generated scripts and are never installed in a game.

Run `Tools/Build-GameScriptVariants.ps1` after an edit. Run it with `-Check` in CI to reject missing, stale, or unexpected generated modules. On Windows, double-click `Tools/Build-GameScriptVariants.cmd`; it keeps the window open so errors remain readable.

The source extension defines the script kind and is preserved in both distributions:

| Extension | Usage |
| --- | --- |
| `.nut` | Classic Squirrel script associated with a precise context such as server, client, or UI. |
| `.gnut` | Global NUT script providing global declarations or functions and commonly loaded in multiple VMs/contexts. |

The target game never determines the extension. Current runtime and map modules use `.nut` files. `sh_remap.nut` is loaded in both VMs and selects its executable branch with the game preprocessor.

Zipline behavior and endpoint models are shared by R5Reloaded and R5Flowstate. Both variants expose the same orientation, support, arm-height, width, speed, length-scale, automatic-end, fade, cable scale, velocity, drop, auto-detach, rest-point, detach-end, and vertical push-direction settings. Automatic placement detects the model below the horizontal end or the surface below the real upper cable attachment for a vertical zipline. A vertical zipline always places its bottom directly below that attachment, including arm offsets; its push-off angle is a world yaw, independent of the endpoint and support rotations.

The scene preview draws valid start/end auto-detach distances as red cable segments. They disappear when their combined distance would overlap on a cable that is too short.

## Installation contract

Place the six `.nut` modules for the selected game in `platform/scripts/vscripts/remap/`. Load `sv_remap_objects.nut`, `sv_remap_ziplines.nut`, `sv_remap_map.nut`, then `sh_remap.nut` in the server context. Load `cl_remap_objects.nut`, `cl_remap_map.nut`, then `sh_remap.nut` in the client context. Call `Sh_ReMap_Init()` from `sh_init.gnut` on R5Reloaded and from `_sh_init.gnut` on R5Flowstate.

The app preserves the surrounding files and replaces only these function bodies:

- `Sh_ReMap_PrecacheMap()` in `sh_remap.nut`;
- `Sv_ReMap_LoadMap()` in `sv_remap_map.nut`;
- `Cl_ReMap_LoadMap()` in `cl_remap_map.nut`.

Every selected map source is resolved to the exact RPAK files that exist in the active installation. The edited map's own archives are left to the normal level loader. Additional main, `_client_perm`, and `_client_temp` archives are emitted as SDK `pak_requestload` commands before generated model precaches; missing archive variants are never guessed or emitted. Live rebuild commands request the same additional archives before recreating the map.

Build enables `REMAP_LOAD_MAP`; Reset restores the default empty map functions, the placeholder precache, and disables `REMAP_LOAD_MAP`. This keeps custom comments and future surrounding file changes intact. The app never edits `scripts.rson`; add and maintain the required `SERVER` and `CLIENT` entries manually.

The generated-output window has separate **Scripts** and **ENT** views. The ENT view displays the exact additions generated for `_script.ent`, `_snd.ent`, and `_spawn.ent`; original base-map entities are merged or excluded only during export. Both views preserve long generated lines with horizontal scrolling.

**Build and install map** provides one export workflow. **Optimize with native ENT files** is enabled by default and installs the native ENT representation. Disable it to generate and install only the `.nut` map modules. Native ENT installation resets the generated `.nut` map modules by default so an older script export cannot spawn duplicate objects; this reset can be disabled, and the separate reset command remains available. The dialog warns before export when the selected representation cannot faithfully generate some objects: ziprails require native ENT files, while script-only objects require `.nut`. Either representation can optionally reload its target map after installation, and the Live window exposes the same explicit reload action. Reload is disabled by default and sends a validated `map mp_...` command through the configured live connection.

When replacing an existing generated map, ReMap creates a one-time `.remap.bak` backup of each edited map module.
